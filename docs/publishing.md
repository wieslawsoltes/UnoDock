# Build and release configuration

## Continuous integration

`CI` (`ci.yml`) runs on every pull request, on pushes to `main` and on manual dispatch. It
checks sources and portable tests, runs the desktop suites in real Uno hosts on Windows,
macOS and Linux, packs the packages, and publishes the browser head with a Playwright smoke
test. A manual run with `full` set runs every desktop suite on every platform and every
browser spec; do that before a release. [Build and verification](testing.md) lists the jobs.

The `NuGet packages` job packs every packable library on `windows-latest` with the CI-only
version `0.0.0-ci.<run number>`, verifies the result and uploads the `nuget-packages-ci`
artifact. It never publishes. A build-only platform is not reported as runtime-tested, and a
successful CI package build is not evidence of a published release.

Native WinUI XAML packing uses Visual Studio MSBuild (`microsoft/setup-msbuild`) rather than
`dotnet` MSBuild, because its XAML compiler task requires that host.

## Packages

`tools/nuget-packages.py` discovers packages instead of listing them: every
`src/<Name>/<Name>.csproj` whose `IsPackable` does not evaluate to `false` is packed and
verified. A new library under `src/` is released with no workflow change.

| Package | Contents |
|---|---|
| `UnoDock.Core` | Portable geometry, drag state machine, update batching and layout snapshots (`net10.0`). |
| `UnoDock` | Uno Platform controls (`net10.0`) and the native WinUI build (`net10.0-windows10.0.26100`). |
| `UnoDock.Themes.Aero`, `UnoDock.Themes.Metro`, `UnoDock.Themes.VS2010` | Classic themes for both builds. |

`UnoDock.Browser` is not packed yet (`IsPackable=false`). Its JavaScript shell modules must
be served by a host page that embeds the Uno application, and that host template is not
published; until it is, the browser workspace is used from source, as in the browser
workbench. Every package ships XML documentation for IntelliSense.

Shared metadata lives in `Directory.Build.props`: authors, copyright, MIT license expression,
project and repository URLs, tags, README, icon (`build/icon.png`, regenerated by
`tools/generate-package-icon.py`) and release-notes link. Packages are deterministic, embed
untracked sources, publish SourceLink repository metadata and produce `.snupkg` symbol
packages. Package validation runs for plain SDK projects; Uno.Sdk projects skip it because
their generic Uno and native WinUI surfaces intentionally differ.

Verification fails when a package has an unexpected identity or version, a missing or extra
`lib/<tfm>/` folder, a foreign assembly, a PDB or source file, an undeclared content file,
any unexpected entry, missing README/icon/license/repository commit, a sibling dependency at
another version, or a symbol package whose portable PDBs lack deterministic SourceLink for the
same commit. To reproduce locally without the Windows target framework:

```sh
python3 tools/nuget-packages.py pack   --output artifacts/packages -p UnoDockLibraryFrameworks=net10.0
python3 tools/nuget-packages.py verify --output artifacts/packages -p UnoDockLibraryFrameworks=net10.0
```

## Trusted publishing

`Publish NuGet` (`publish.yml`) uses [nuget.org Trusted Publishing](https://learn.microsoft.com/nuget/nuget-org/trusted-publishing).
GitHub issues the workflow an OIDC token, `NuGet/login` exchanges it for an API key valid for
about an hour, and the repository stores no NuGet API key.

| Job | Runner | Purpose |
|---|---|---|
| `validate` | Ubuntu | Resolves the version, checks the tag and stable-release rule, runs portable tests, the generated-adapter check and the metadata gate. |
| `pack` | Windows | Packs and verifies every package with `-p:Version` and `ContinuousIntegrationBuild=true`. |
| `attest` | Ubuntu | Records SLSA build provenance for each `.nupkg` (`id-token`/`attestations: write`). |
| `publish` | Ubuntu, environment `nuget` | Exchanges OIDC for a key and pushes packages and symbols with `--skip-duplicate`. |
| `release` | Ubuntu | For tags, creates the GitHub release with that version's section of `CHANGELOG.md` as its notes and attaches the packages (`contents: write` in this job only). |

### One-time setup

1. **nuget.org policy.** Signed in as the package owner, open *Trusted Publishing* from the
   account menu and add a GitHub Actions policy: owner `wieslawsoltes`, repository `UnoDock`,
   workflow file `publish.yml`, environment `nuget`. The policy applies only to runs of that
   workflow file in that environment.
2. **Repository variable.** Under *Settings → Secrets and variables → Actions → Variables*,
   create `NUGET_USER` with the nuget.org user name (not e-mail address) that owns the policy.
   It is a variable, not a secret; it grants nothing without a matching policy.
3. **Environment.** Under *Settings → Environments*, create `nuget`. Adding required reviewers
   is recommended so every push waits for approval, and limiting deployment to `main` and
   tags matching `v*` keeps other refs out.
4. Remove any legacy `NUGET_API_KEY` secret and revoke that key on nuget.org; the workflow no
   longer reads it.

Workflow files cannot create nuget.org policies or GitHub settings; these steps are manual.

### Cut a release

Add a `## <version>` section to `CHANGELOG.md`, run CI with `full` set on that commit, then
tag the commit on `main` with `v` followed by the SemVer 2.0 version and push the tag:

```sh
git tag v0.1.0-preview.1
git push origin v0.1.0-preview.1
```

The tag must identify a commit on `main` whose `CI` run succeeded, and `CHANGELOG.md` must
have a section for the version. Versions with a prerelease suffix produce a GitHub
prerelease. Re-running a partially failed release is safe: nuget.org skips versions it
already has, and existing release assets are replaced.

### Dry runs

Run *Actions → Publish NuGet → Run workflow* with a version. `dry-run` defaults to `true`:
the run validates, packs and verifies, and uploads `nuget-packages` as an artifact, but does
not attest, push or create a release. Clearing `dry-run` publishes and is accepted only on
`main`; tags are the normal release path.

### Verify provenance

Each published `.nupkg` has a GitHub build-provenance attestation that binds its SHA-256
digest to the workflow run and commit. Verify the files attached to the GitHub release (or
the run's `nuget-packages` artifact):

```sh
gh release download v0.1.0-preview.1 --repo wieslawsoltes/UnoDock --pattern '*.nupkg'
gh attestation verify UnoDock.0.1.0-preview.1.nupkg --repo wieslawsoltes/UnoDock
```

A copy downloaded from nuget.org carries an added nuget.org repository signature, so its
digest differs from the attested file and does not verify.

## Stable-release attestation

A stable 1.0+ release requires `contracts/release-attestation.json` with
`fullCompatibilityVerified: true` and a matching `sourceTreeSha256`. Compute the latter with
`python3 tools/source-fingerprint.py` after committing the verified source. The fingerprint
covers the tracked tree except the attestation itself, avoiding an impossible
self-referential commit hash. Any other tracked change invalidates it. Prereleases and 0.x
versions do not require it.

The preview intentionally provides no full-compatibility attestation. Its package metadata
and README disclose remaining API, behavior, windowing and platform limits. An attestation is
an explicit reviewed assertion, not a substitute for acceptance tests.
